# 专家评审意见回应与设计收敛

> 日期：2026-11-16  
> 对应文档：`docs/adaptive-scan-design-review.md`  
> 结论：专家意见整体合理，建议采纳大部分；原方案需要收敛，不需要重写扫描器

---

## 1. 总体判断

专家意见与实测数据基本一致：

```text
方向正确：增量改造、业务影响优先、observe -> safe -> auto
需要收敛：不要第一版就做完整自学习/多闭环
必须修正：设备指标不能直接做外部 IO 减法
必须修正：worker 不能因延迟升高而自动扩张
必须修正：冷/热不能作为二元分类
必须修正：impact 不能映射成模糊的“设备占用百分比”
```

原方案不是“错”，而是**第一版范围过大**。  
建议把它拆成：

```text
P0：指标口径 + 设备压力 + observe + 修正控制器误判
P1：单控制器、QPS 主控、worker 固定/受限、准入与暂停
P2：存储类型、网络盘、多设备预算
P3：热/冷状态、自学习、自动升速
```

## 2. 对专家意见逐条判断

| 专家意见 | 判断 | 依据 | 决策 |
|---|---|---|---|
| 基于现有源码增量改造，不重写扫描器 | 同意 | 现有 Scanner、worker pool、token bucket、配置热更新、断点续扫已具备 | 保留现有架构，只扩展 performance/scanner |
| `%util` 不能作为唯一业务保护指标 | 同意 | beegfs01 停止 dirspace 后 sdb 仍 93.9%，storage-prod 在占盘 | `%util` 只作趋势；主看 await、aqu-sz、p95、PSI |
| 设备总 IOPS 减 dirspace IOPS 不可直接实现 | 同意，且应删除该设计 | `/proc/diskstats` 是设备级；QPS 不等于 IOPS；元数据可能命中缓存 | 第一阶段不做精确归因；优先 cgroup v2 `io.stat` 或相对压力 |
| QPS 主控、worker 从属方向正确 | 同意 | 冷数据 64 worker 时 aqu-sz 48～73，worker 越多队列越长 | v1 worker 固定上限；控制器只调 QPS 和有效并发 |
| worker 不能因在途请求增加而自动扩张 | 同意 | 延迟升高 → 在途增加 → worker 增加 → 队列更长，是正反馈 | 删除“按观测延迟扩 worker”；worker 只作为上限 |
| 冷/热不能只靠 IO/QPS 比值 | 同意 | 业务 IO、readdir/lstat 差异、采样窗口都会干扰 | 改为 HOT / MIXED / IO_BOUND 三状态 |
| impact 需要明确定义 | 同意 | “设备占用 20%～25%”未定义是 util、IOPS 还是延迟预算 | impact 定义为行为策略，不是固定性能参数 |
| 精确扫描需要准入，但不强制所有环境维护窗口 | 同意 | 独占 SSD 与共享 HDD 风险不同 | 共享/未知默认保守；独占可自动；准入+运行时双检查 |
| 96% 满盘与扫描性能分开 | 同意 | 容量风险不等于随机读性能线性下降 | 作为准入风险信号，不进入 QPS 公式 |
| 第一版不要做自学习 | 同意 | 当前 CPU 口径、设备采集、外部归因都未确认 | P0 只 observe；P3 再自学习 |
| CPU 口径必须统一 | 同意，且应升级为 P0 最高优先级 | 配置 60%，实测进程约 7.2～8.0 核；CPUGuard 是逐调用 sleep，不是全局硬限制 | 先修 CPU 语义/全局约束，再谈自动 QPS |

## 3. 需要补充专家未强调的点

### 3.1 QPS 限速值和实际 QPS 不是一回事

token bucket 有突发容量，实测实际 QPS 可以高于配置上限。  
控制器必须使用**实测 QPS**，不能只看 `max_metadata_qps`。

### 3.2 元数据延迟不等于设备延迟

- 元数据 p95 可能因为 cache 很低
- 设备 await 可能已经很高
- 两者必须分开采集、分开判断

### 3.3 多 root / 多挂载点必须按底层设备聚合

```text
一个设备一个预算
不能两个 root 各自以为拥有整块盘
```

否则多目录同时扫描会叠加压力。

### 3.4 网络盘需要单独降级路径

NFS/CIFS：

```text
没有本地 diskstats
cgroup io.max 不一定适用
只能看 p95、错误、超时、RPC 统计
```

不能把 HDD 的 await 策略套到网络盘。

### 3.5 基线不能被业务污染

如果采样时业务已经在高负载，所谓“基线”就是错的。  
需要：

```text
无 dirspace 负载时采样
或使用长期低分位数
或直接进入保守模式
```

## 4. 修订后的第一版设计

### 4.1 保留

- 现有 Scanner / worker pool
- 现有 token bucket
- 现有配置热更新
- 现有断点续扫、目录索引、原子发布

### 4.2 第一版只做

```text
1. 统一 CPU 口径，修全局 CPU 约束
2. 采集设备 await / aqu-sz / IOPS / PSI
3. observe 模式：只记录，不改变扫描
4. 设备压力高时禁止继续升 QPS
5. 业务忙时暂停/推迟
6. worker 固定上限，不自动扩张
7. impact: low / balanced / fast 的行为定义
8. 准入检查 + 运行时检查
```

### 4.3 第一版不做

```text
不做自学习
不做自动 worker 扩张
不做设备 IOPS 减法归因
不做复杂冷热分类
不默认所有精确扫描都进维护窗口
```

---

## 5. 修订后的 impact 定义

| impact | 行为目标 | 具体策略 |
|---|---|---|
| low | 业务风险最低 | 设备/业务有压力就暂停；只在明显空闲时扫描；不追求速度 |
| balanced | 兼顾 | 有压力降速；低压力逐步升速；保留余量 |
| fast | 维护窗口优先完成 | 可提高预算；仍有硬保护和业务暂停 |

不再写：

```text
low = 设备占用 20%～25%
```

因为“设备占用”无法用单一指标定义。  
改为：

```text
low = 任一压力信号超预算就退让
balanced = 压力低时用余量
fast = 维护窗口内允许更高预算
```

---

## 6. 修订后的控制关系

```text
一个控制器
  ├─ 输入：设备压力、业务压力、自身 p95、CPU、PSI
  ├─ 输出：QPS 目标
  ├─ 输出：worker 有效并发上限（只降不升）
  └─ 输出：暂停 / 恢复
```

worker 不作为独立积分器：

```text
worker 上限在扫描开始时确定
压力高时降低有效并发
压力低时不因为延迟下降而自动增加
```

---

## 7. 最终结论

专家意见合理，应该采纳以下核心修正：

```text
1. 不做设备 IOPS 减法
2. 不把 %util 当唯一依据
3. 不让 worker 因延迟升高而扩张
4. 冷/热改为三状态
5. impact 定义为行为，不是百分比
6. 精确扫描按环境准入，不强制所有环境维护窗口
7. 96% 容量问题单独处理
8. 第一版只做 observe + 压力保护，不做自学习
```

原方案的方向保留：

```text
业务影响优先
相对压力
QPS 主控
worker 从属
快降慢升
按设备共享预算
observe -> safe -> auto
```

一句话：

```text
不是推翻原方案，而是把第一版从“完整自适应系统”
收敛为“可观测、可保护业务、可逐步扩展的控制器”。
```
