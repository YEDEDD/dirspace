# dirspace 技术讨论简报

> 主题：在超大共享文件系统上，如何做到“任意子目录、精确、第一次就比 du 快”的目录空间统计  
> 版本：2026-11-11  
> 用途：给存储/文件系统/分布式系统专家讨论，不限于代码实现

---

## 0. 一页结论

当前 `dirspace` 已经做到：

- 后台扫描一次，结果写本地 SQLite，日常查询不访问共享存储
- 精确模式遍历全部文件元数据，结果是精确的
- 树状目录可以并行扫描
- 支持可配置深度的目录索引，v1.7.0 新增 `index_all_dirs` 和 `size` 命令

但核心目标还没有被证明达成：

> **任意子目录 + 精确 + 第一次扫描 + 比 `du -sh` 快 + 上亿小文件 + 单客户端**

这是一个“元数据遍历下界”问题，不是单纯的代码优化问题。当前的主要瓶颈是：

1. 单客户端元数据吞吐有限
2. 单个目录的 `readdir` 天然串行
3. 8TB 子目录如果很扁平，无法靠拆子目录并行
4. 厂商目录配额只能覆盖最多 1000 个目录，不能覆盖任意目录
5. 实际挂载可能是 CFS Turbo 私有客户端（`mount.lustre`），不是 NFS，之前规划的 NFS READDIRPLUS 可能不适用
6. 多客户端分片扫描和结果合并还没有实现

需要专家一起判断的是：  
**在现有 CFS/Lustre 能力下，任意目录精确统计的最快路径是什么；是否必须上多客户端；单客户端还有多少优化空间；是否值得投入厂商 quota/API 或改目录布局。**

## 1. 业务目标与验收标准

### 1.1 业务场景

- 腾讯云 CFS，文件系统容量约 **70TiB**
- 约 **11 亿级文件**、**130 万级目录**（最近一次根目录精确结果）
- 某个业务子目录 `.../map` 至少 **8TB**，小文件很多
- 当前用 `du -sh` 统计 `map` 需要数小时甚至更久
- 业务需要知道“哪个目录占了多少空间”，并希望随时下钻到任意子目录

### 1.2 期望效果

1. 第一次就能较快得到 `map` 的精确大小，最好明显快于 `du -sh`
2. 扫描一次后，任意子目录可以秒级查询
3. 空间变大或变小，下一次刷新能看到
4. 后台定期跑，尽量不影响业务
5. 快速模式可以近似，但**精确模式必须真精确**
6. 多挂载点、多个存储根可管理

### 1.3 明确不接受的方案

- 为了快而返回抽样估算，却宣称精确
- 第一次扫描不比 `du` 快，结果还不准
- 只能查一级目录，查不了 `map` 这种深层目录
- 每次查询都重新遍历 NFS/CFS

### 1.4 建议的验收口径

同一台客户端、同一时段、同一挂载点，顺序执行：

```bash
time du -sh --one-file-system <target>
time dirspace scan --path <target>
```

验收要求：

- `dirspace` 结果是精确值，不是抽样
- `dirspace` 第一次扫描耗时 < `du`
- 第二次查询 `dirspace size --path <target>` 不访问共享存储，秒级返回
- 统计口径与 `du` 对齐：默认 allocated（`st_blocks × 512`），可切换 logical（`st_size`）
- 明确 hardlink、symlink、sparse file 的统计规则

## 2. 当前架构

### 2.1 组件

```text
cmd/dirspace
  └─ internal/cli          命令行、JSON/文本输出、参数校验
       └─ internal/service 业务编排：扫描、查询、partial、size、daemon
            ├─ internal/scanner   目录遍历、QPS 控制、聚合
            ├─ internal/storage   SQLite 持久化、任务状态、索引
            ├─ internal/performance 并发、限速、CPU/内存保护
            └─ internal/mountinfo 挂载点识别
```

- 单一静态二进制，Go 实现
- 本地 SQLite WAL 缓存，数据库不放在共享存储上
- 只读文件元数据，不读文件内容，不写扫描根目录
- systemd 常驻 daemon，也支持手动 `scan` / `quick`

### 2.2 扫描流程

```text
扫描根
  ├─ 枚举一级子目录
  ├─ 每个一级子目录一个逻辑任务
  │    └─ 共享 treeQueue
  │         ├─ 目录任务：open + readdir，发现子目录/文件
  │         └─ 文件任务：批量 lstat，累计大小
  └─ 汇总一级目录，写 staging，成功后原子发布
```

关键点：

- **精确模式**：遍历所有目录项，对所有文件 `lstat`，结果是精确的
- **快速模式**：按 salted path hash 抽样约 2% 文件，并用目录前 32 个文件做 census，加权估算；结果标记 `sampled`，不是精确值
- **树状并行**：一级目录之间并行；一级目录内部，目录任务和文件批次共用 worker 队列
- **flat 目录**：`readdir` 本身串行，但读出的文件可以批量分发给多个 worker 做 `lstat`
- **QPS 控制**：元数据操作客户端限速；profile 默认 low=100、normal=300、fast=1000，可自适应
- **硬链接**：有去重登记；符号链接不跟随
- **断点续扫**：按目录保存 staging，重启后可恢复；续扫**不会重建目录索引**

### 2.3 持久化模型

SQLite schema v6，核心表：

| 表 | 作用 |
|---|---|
| `roots` | 扫描根、总容量、文件数、目录数、状态、准确性 |
| `scan_runs` | 每次扫描任务、进度、QPS、耗时、错误 |
| `run_dirs` | 当前运行的 staging 一级目录结果 |
| `top_dirs` | 已发布的正式一级目录结果 |
| `dir_index` | 目录下钻索引，路径、父路径、深度、聚合大小 |
| `dir_history` | 历史统计 |
| `hardlink_seen` | 硬链接去重 |
| `control` | 跨进程 pause/resume/cancel |

发布策略：

- 扫描过程中写 `run_dirs`，不覆盖正式结果
- 完整成功后，`top_dirs` 和 `dir_index` 原子替换
- 失败或中断保留上次有效数据
- `partial` 可以把本轮已完成目录和上次结果合并展示，但明确标记来源

### 2.4 查询能力

| 命令 | 作用 | 是否访问共享存储 |
|---|---|---|
| `top` / `list` | 一级目录排名 | 否 |
| `children --path` | 某个目录的直接子目录 | 否 |
| `size --path` | 某个目录的缓存大小 | 否 |
| `size --path --exact` | 未命中时把目标目录作为独立根精扫 | 是，第一次 |
| `partial` | 扫描中合并本轮和上次结果 | 否 |
| `status` | 进度、QPS、ETA、数据库状态 | 否 |

### 2.5 目录索引现状

- 默认 `index_depth: 3`、`index_top_k: 20`
- 一级目录全部保留；更深层只保留每个父目录 top K
- 因此 `map` 这种排不进前 20 的子目录会查不到
- v1.7.0 新增 `index_all_dirs: true`：每个目录存一行聚合大小，可查任意深层路径
- 全目录索引的代价：130 万目录约几百 MB；目录上亿时数据库会显著变大
- `index_all_dirs` 只对新的完整扫描生效；续扫不会重建
- `size --exact` 会把目标目录注册成一个**新的独立根**，不会合并回上级根

## 4. 疑难杂症

### 4.1 第一次精确扫描不一定比 du 快

`du` 也是元数据遍历，而且通常是单线程。`dirspace` 的机会是并行：

- 多个一级目录并行
- 一级目录内部多个子目录并行
- 文件 `lstat` 批量并行

但如果：

- 目录很扁平，`readdir` 串行
- NFS/CFS 客户端或服务端已经饱和
- 单个客户端元数据队列有限

那么并行不会更快，甚至更慢。

**目前没有完成同机同盘的严格 benchmark，这是第一优先要补的实验。**

### 4.2 单目录 readdir 串行

一个目录的 `readdir` 是一个目录流，通常只能顺序读。能并行的只有：

- 读完一批目录项后，并行 `lstat` 文件
- 把子目录分给多个 worker 继续扫

如果 `map` 下面直接是几百万个文件，没有子目录可拆，那么：

- 枚举阶段串行
- 只能靠 `lstat` 并行和 READDIRPLUS 类优化
- 提升有上限

### 4.3 8TB 的 map 可能是扁平结构

需要确认：

```bash
find <map> -maxdepth 1 -type d | wc -l
find <map> -maxdepth 1 -type f | wc -l
```

- 如果一级子目录很多：可以并行，适合多客户端分片
- 如果直接文件很多：单目录瓶颈，分片和并行都受限
- 如果是混合：按子目录分片，根目录文件单独处理

### 4.4 目录索引与任意路径的矛盾

- 默认 topK/depth 索引无法覆盖任意路径
- 全目录索引可以覆盖，但：
  - 只在新完整扫描后生效
  - 数据库会变大
  - 仍然需要先扫描一次
- `size --exact` 可以只扫目标子树，但会创建独立根，不自动合并到上级根

### 4.5 NFS 与 CFS Turbo 私有客户端的路线冲突

厂商反馈：

- 当前实例是 **Turbo 系列**
- 使用 **私有客户端 `mount.lustre`**
- 不是 NFS

如果实际挂载确实是 `lustre`：

- NFSv3 READDIRPLUS 优化不适用
- 之前关于 `nconnect`、`actimeo`、NFS RPC 的讨论都不适用
- 需要转向 Lustre 私有客户端的元数据能力

如果实际挂载是 NFS：

- 需要确认为什么 Turbo 实例会以 NFS 挂载
- 可能是通用 CFS，或中间有别的网关
- READDIRPLUS 才值得评估

**必须先确认：**

```bash
findmnt -T /mnt
stat -f -c %T /mnt
mount | grep -i cfs
```

### 4.6 厂商目录 quota 只能覆盖少量目录

厂商反馈的能力：

- `DescribeUserQuota` 可按目录返回 `CapacityUsed`（GiB）和 `FileUsed`（文件数）
- 前提是目录已建配额条目
- 单文件系统最多 **1000 个目录配额**
- 父目录和子目录不能同时配
- 不支持任意路径、路径前缀、PVC、子卷维度
- 不返回子目录数
- 限频 20 次/秒
- 配额是硬限制；`0/0` 是否等于“只统计不限制”，需要厂商书面确认
- 路径是 `/cfs/...` 内部逻辑路径，不是本地挂载路径

结论：

- 对 `map`、`cae365` 这类少量关键目录，quota 可以做到 O(1) 精确查询
- 对“130 万目录任意查询”，quota 不是解法
- 自动创建 `0/0` 配额有业务写入风险，不能贸然做

### 4.7 元数据规格可能不匹配

厂商反馈：

- 当前元数据类型是 `basic` 标准版
- 官方建议标准版用于文件数 <15 亿、平均文件大小 1MiB–1TiB
- 8TB 小文件目录更接近增强版元数据场景
- 元数据类型创建后暂不支持调整

这意味着：

- 即使软件优化，底层元数据性能可能仍是瓶颈
- 需要和厂商确认 10 亿文件 + 标准版元数据的实际风险
- 可能需要接受“扫描时间无法数量级下降”，或迁移/重建文件系统

### 4.8 没有可靠的实时变化追踪

- NFS 客户端没有可靠的远程 inotify
- Lustre 有 Changelog 能力，但需要服务端开启和额外消费逻辑，不是当前实现
- 目录 mtime 不能可靠反映文件大小变化
- 当前只能定期 quick/exact 扫描

### 4.9 单客户端没有分片和合并

- 当前 daemon 只在一个客户端上跑
- 多个根是串行扫描
- 没有 `--shard`，没有多客户端结果合并
- SQLite 是本地单库，不适合多客户端并发写同一份

### 4.10 统计口径风险

需要明确：

- allocated vs logical：`du` 默认 allocated，`du --apparent-size` 是 logical
- hardlink：是否只计一次
- symlink：是否跟随
- sparse file：按块还是按逻辑大小
- CFS/Lustre 客户端的块大小、stripe、压缩/去重是否影响

### 4.11 关键未知量

在专家讨论前，以下数据必须补齐，否则方案选择会失真：

| 未知量 | 为什么要紧 | 怎么确认 |
|---|---|---|
| `/mnt` 实际是 `lustre` 还是 `nfs` | 决定 READDIRPLUS/NFS 调优是否适用 | `findmnt -T /mnt`、`stat -f`、`mount` |
| `map` 是树状还是扁平 | 决定能否并行/分片 | `find map -maxdepth 1` 统计目录/文件数 |
| `du -sh map` 实际耗时 | 验收基线 | 同机同盘实测，重复 2 次 |
| `dirspace scan map` 实际耗时 | 判断单客户端是否够快 | 同机同盘实测 |
| 单客户端元数据 OPS 上限 | 决定多客户端收益 | 压测 + 厂商确认 |
| CFS 服务端剩余元数据余量 | 决定能否多客户端 | 厂商监控/压测 |
| quota 刷新延迟、`0/0` 语义 | 决定 quota 能否用于生产 | 厂商书面确认 |
| `map` 的硬链接/稀疏文件比例 | 决定统计口径差异 | `find`/抽样检查 |

### 4.12 QPS 观测异常

曾观测到实际 QPS 高于配置上限（如 1729 / 1000）。可能原因：

- 线上还是旧二进制
- 统计窗口和限速窗口不一致
- 部分元数据路径未经过限速

需要复核，不能带着这个不确定性做容量规划。

## 5. 可选技术路线

### 5.1 路线对比

| 路线 | 精确 | 任意目录 | 第一次比 du 快 | 工作量 | 风险 | 适用 |
|---|---|---|---|---|---|---|
| 单客户端并行 exact（当前） | 是 | 扫描后 | 可能 | 低 | 低 | 树状目录，先验证 |
| 全目录索引 + `size` | 是 | 是 | 否 | 已完成 | 中（DB 变大） | 查询加速 |
| 多客户端分片 + 合并 | 是 | 是 | 可能显著 | 高 | 高 | 大根、树状目录 |
| 厂商目录 quota | 是 | 仅 1000 个 | O(1) | 中 | 中 | 关键目录 |
| NFS READDIRPLUS | 是 | 是 | 可能 | 高 | 高 | 仅 NFS |
| Lustre 私有客户端优化 | 是 | 是 | 未知 | 高 | 高 | 需厂商支持 |
| 数据布局拆小目录 | 是 | 是 | 长期有效 | 高（业务改造） | 高 | 扁平大目录 |
| 抽样估算 | 否 | 是 | 是 | 低 | 低 | 仅趋势，不可精确 |
| 增量/Changelog | 是 | 是 | 首次仍慢 | 高 | 高 | 变更追踪 |

### 5.2 单客户端并行 exact（当前基线）

已实现：

- `treeQueue` 同时处理目录任务和文件批次
- 子目录并行
- 文件 `lstat` 并行
- QPS 限速和自适应保护

需要补：

- 严格 benchmark
- 并发/QPS 调优
- 批次大小调优
- 验证 `readdir` 和 `lstat` 的 RPC/耗时占比

优点：改动小，风险低。  
缺点：受单客户端和服务端上限约束。

### 5.3 多客户端分片 + 合并

思路：

```text
coordinator
  ├─ 把根按一级/二级目录分片
  ├─ 每台客户端扫一个 shard，写本地 SQLite/JSON
  └─ merge 按路径汇总，父目录求和
```

需要设计：

- 分片规则：按目录列表、按 hash、按大小均衡
- 任务租约：避免重复扫、支持失败重试
- 合并：路径、父目录、硬链接去重、统计口径一致
- 一致性：不同 shard 扫描时间不同，不是同一时刻快照
- 限流：多客户端总 QPS 不能压垮 CFS

优点：最有可能显著缩短第一次扫描时间。  
缺点：架构复杂，运维复杂，扁平单目录仍然无法分片。

### 5.4 厂商目录 quota

已确认能力：

- `DescribeUserQuota` 返回目录级 `CapacityUsed` / `FileUsed`
- 1000 个目录上限
- 20 QPS
- 硬限制
- 路径格式 `/cfs/...`

可以做的集成：

- 只读拉取 quota 列表
- 映射到本地路径
- 写入缓存，来源标记 `quota`
- `size --quota` 查询
- 不自动创建配额，等 `0/0` 语义确认

优点：关键目录 O(1)，不扫盘。  
缺点：覆盖面小，不是核心解法。

### 5.5 NFS READDIRPLUS

仅当实际是 NFS 时考虑：

- 一次 READDIRPLUS 返回目录项和属性，减少 `readdir + lstat`
- Go 标准库不暴露，需要 libnfs/cgo 或自研 NFS 客户端
- 先看内核是否已经使用 READDIRPLUS，避免重复优化

如果实际是 Lustre 私有客户端，此路线不适用。

### 5.6 Lustre 私有客户端能力

需要向厂商/专家确认：

- 私有客户端是否提供目录级递归统计 API
- `lfs` 工具是否有 `lfs find` 之外的聚合能力
- 是否支持 project quota、目录 quota、Changelog
- 单客户端元数据并发上限
- 是否有官方并行扫描工具或 SDK

### 5.7 数据布局改造

如果 `map` 是几百万文件的扁平目录：

- 按业务/时间/hash 拆成多级子目录
- 让每个目录变小，`readdir` 变快
- 让扫描可以并行
- 这是长期最有效的办法，但需要业务改写入路径

### 5.8 增量与变更追踪

- NFS：没有可靠远程事件，基本只能定期扫描
- Lustre：Changelog 可以记录元数据变更，但需要服务端开启、消费、回放，工程量大
- 目录 mtime 只能发现目录项变化，不能发现文件大小变化
- 短期内不建议把增量作为核心依赖

---

## 5.9 运行约束

方案必须满足：

- 只读元数据，不读文件内容，不写扫描根目录
- 客户端 CPU、内存、元数据 QPS 可限制
- 数据库必须放本地盘，不能放共享存储
- 多客户端方案要能控制总 QPS，不能压垮业务
- 扫描结果要能区分精确、抽样、部分、过期
- 任何“只统计”的 quota 操作不能意外变成硬限制，影响业务写入

## 6. 厂商已确认的约束

以下来自厂商反馈，需在专家讨论中作为输入：

| 项目 | 结论 |

## 10. 一句话总结

**当前 dirspace 是一个“单客户端、精确遍历、本地 SQLite 缓存”的目录统计工具；它已经把重复查询变成了 O(1)，但还没有解决“第一次精确扫描比 du 快”这个核心问题。下一步要么证明单客户端并行已经足够快，要么上多客户端分片；quota 和 READDIRPLUS 都只是局部补充，不是任意目录精确统计的通用解。**
